# AGENTS.md

## Commands

- `pnpm dev` — dev server at `http://localhost:3000` (admin at `/admin`). pnpm is required (`packageManager: pnpm@11.0.8`); no lockfile is committed, so a fresh install resolves deps fresh. Inside a parent workspace, use `pnpm ii` (runs with `--ignore-workspace`).
- `pnpm lint` / `pnpm lint:fix` — ESLint.
- **There is no `typecheck` script.** Use `pnpm exec tsc --noEmit`. (`pnpm build` also typechecks, but it needs a database.)
- `pnpm test:int` — Vitest integration tests (`tests/int/**/*.int.spec.ts`).
- `pnpm test:e2e` — Playwright; it starts `pnpm dev` itself (`reuseExistingServer: true`, so an already-running dev server is reused).
- `pnpm test` — runs int, then e2e.

Verification order: `pnpm lint` → `pnpm exec tsc --noEmit` → `pnpm test:int`.

Run a single test:

```bash
pnpm exec vitest run tests/int/api.int.spec.ts
pnpm exec playwright test tests/e2e/frontend.e2e.spec.ts
```

There is no CI and no pre-commit hook — nothing runs these checks for you.

## Tests need a real database

Both suites boot Payload against `POSTGRES_URL` from `.env`; nothing is mocked or fixture-backed. `.env` must exist first (`cp .env.example .env`). `tests/e2e/admin.e2e.spec.ts` seeds then deletes a user (`dev@payloadcms.com` / `test`) in the real `users` collection via `tests/helpers/seedUser.ts`.

Playwright uses `channel: 'chromium'` — run `pnpm exec playwright install chromium` once.

## Generated files

- `src/payload-types.ts` — regenerated by `pnpm generate:types` (ESLint and Prettier both ignore it). Never hand-edit; fix the collection config instead.
- Admin import map — run `pnpm generate:importmap` after adding or moving admin components.

## Schema changes

Migration history lives in `src/migrations/`. Create one with `pnpm payload migrate:create`; deploys run `pnpm ci` (`payload migrate && pnpm build`). The Postgres adapter sets no `push` flag — per the README, dev defaults to pushing schema directly, so a local schema change may not produce a migration file on its own. Always create one before shipping a collection/field change.

## Architecture

One Next.js 16 app hosting both halves, split by route group:

- `src/app/(payload)` — admin panel and API routes.
- `src/app/(frontend)` — the public site (posts, pages, search, sitemaps, preview).
- `src/payload.config.ts` — Payload config: collections (`src/collections`), globals (`src/Header`, `src/Footer`), plugins (`src/plugins`), DB adapter, Blob storage.
- `src/migrations`, `src/access`, `src/fields`, `src/hooks`, `src/utilities` — shared Payload code.

Path aliases (from `tsconfig.json`): `@/*` → `src/*`, `@payload-config` → `src/payload.config.ts`.

## Conventions and gotchas

- **Style:** Prettier config exists but there is no `format` script — `pnpm exec prettier --write .`. Settings: no semicolons, single quotes, `printWidth: 100`, trailing commas everywhere.
- **Always call tools through the package scripts.** Every script wraps itself in `cross-env NODE_OPTIONS=--no-deprecation` to suppress Payload/Node deprecation noise; running raw `next` or `payload` skips that.
- **Env:** `.env.example` → `.env`, needs `POSTGRES_URL`, `PAYLOAD_SECRET`, `BLOB_READ_WRITE_TOKEN`, `PREVIEW_SECRET`, `CRON_SECRET`, `NEXT_PUBLIC_SERVER_URL`. A `localhost`/`127.0.0.1` connection string switches the adapter to plain Postgres instead of Vercel Postgres.
- **Revalidation:** published content changes revalidate the frontend through `afterChange` hooks. Changing a redirect's `from` field requires a rebuild (the plugin says so in the admin description).
- **Seeding** from the admin panel's "Seed the database" button is destructive — it drops existing content.
- **Cron:** `vercel.json` hits `/api/payload-jobs/run` daily for scheduled publish; the endpoint accepts `Bearer $CRON_SECRET`.
